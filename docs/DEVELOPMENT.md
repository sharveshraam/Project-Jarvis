# Development

## Two ways to build

**Offline** — no Android SDK, no Gradle, no network. This is the primary path and the one CI runs
first:

```bash
./tools/verify_all.sh
```

**Gradle** — the normal Android path, when a toolchain and network are available:

```bash
./gradlew :core:test :app:test     # the same assertions, through a thin JUnit bridge
./gradlew assembleDebug            # debug APK (applicationIdSuffix ".debug")
./gradlew assembleRelease          # unsigned release APK; supply your own keystore
```

Both paths run *identical* assertions. `core/src/test/kotlin/…/AllSuites.kt` is the single registry:
`LocalTestMain` (offline) and `CoreSelfTestJUnit` (Gradle) both iterate it, so the two runners cannot
drift apart. Adding a suite means adding one line there.

## The offline toolchain

`tools/local_core_check.sh` needs only two things and will look for them in this order:

| Tool | Env override | Default lookup |
|---|---|---|
| Kotlin compiler | `KOTLINC=/path/to/kotlinc` or `KOTLIN_HOME=/path/to/dist` | `kotlinc` on `PATH`, then `/tmp/kc/node_modules/kotlin-compiler/bin/kotlinc` |
| Java runtime | `JAVA_HOME` | `java` on `PATH` |

If neither is found it downloads `kotlinc` to `/tmp/kotlinc-dist` and re-executes itself. Compilation
targets JVM 17.

`tools/local_android_check.sh` additionally needs `android.jar` for API 35:

| Source | Notes |
|---|---|
| `ANDROID_JAR=/path/to/android.jar` | explicit |
| `$ANDROID_HOME/platforms/android-35/android.jar` | a normal SDK install |
| `.tools-cache/android-35/android.jar` | gitignored cache |
| `github.com/Sable/android-platforms` (sparse checkout) | community-maintained `android.jar` for every API level; fetched into the cache |

Two details that are easy to get wrong and are handled by the script:

- `kotlinc` must be invoked with **`-no-jdk`** when `android.jar` is on the classpath. Without it the
  JDK's own `java.*` classes collide with the ones inside `android.jar`.
- `:app` references `R.layout.*` / `R.id.*`, and the real `R` class is generated by AAPT2. Offline,
  `tools/generate_local_r.py` produces an equivalent `R.kt` from `res/` so type-checking can proceed.
  It is generated into `build/`, never committed.
- Test sources compile with `-Xfriend-paths`, which is what the Kotlin Gradle plugin does for a test
  source set. Without it the offline runner would be *stricter* than `./gradlew :core:test` and suites
  could not reach internal collaborators such as the NLU rule table.

## What each check enforces

```
tools/verify_all.sh
 ├─ tools/local_core_check.sh      :core compiles, and every suite in AllSuites passes
 ├─ tools/validate_android.py      resources, manifest and view references are self-consistent
 └─ tools/local_android_check.sh   :core + :app type-check against real android.jar (API 35),
                                   then the app's own offline suites run on the JVM
```

`validate_android.py` is what catches the class of bug that otherwise only appears on a device: a
layout id referenced from Kotlin but missing in XML, a manifest component whose class does not exist,
a `@string/` that was never declared, a theme that is not defined. It parses the XML directly, so it
needs no Android tooling.

## Conventions

These are not stylistic preferences; each one exists because the alternative produced a bug.

**`:core` never imports `android.*`.** Not even for a constant. If a piece of logic seems to need the
platform, it needs a port instead. This is what makes the whole brain of the assistant testable in
milliseconds, and `validate_android.py` plus the type-check will both fail loudly if it is violated.

**Framework APIs only, `findViewById` not view binding.** View binding generates classes implementing
`androidx.viewbinding.ViewBinding`, which would drag in AndroidX and break the zero-dependency rule.

**A capability that cannot work says so.** Port methods return `PortResult`, and `Denied` carries a
`capabilityId` that maps to a catalogue entry with a status, an explanation, a remedy, and — for
`NOT_POSSIBLE` — the `androidLimitation`. Never return a success-shaped default for something that did
not happen.

**Time comes from `ClockPort`.** No `System.currentTimeMillis()` in logic; inject the clock and use
`FixedClock` in tests. Every temporal test in the repo pins a known local instant and computes the
expected value independently rather than reading it back from the parser.

**Comments explain *why*, not *what*.** The codebase is heavily commented, but the comments carry the
reasoning that would otherwise be lost: why a rule is narrow, why a fraction is 0.55/0.45, why a
negation guard exists, which real failure a line prevents. If a comment restates the code, delete it.

**Test names are sentences about behaviour.** `"an explicit evening time beats the daypart word next
to it"`, not `"testParseEvening"`. A failing suite should read as a list of broken promises.

**Deterministic before clever.** The NLU is a rule table, the embedder hashes, the lexical index is
BM25, the crypto is pure Kotlin. Neural components are *slots* (`LocalModelPort`, `IntentReranker`)
that can only adjust what the deterministic layer already produced.

## Adding a subsystem

The order matters, because each step keeps the build green:

1. **Model it** in `core/…/model/` — plain data classes, no Android, no I/O.
2. **Declare the port** in `core/…/ports/` returning `PortResult`, with `Denied` carrying a
   `capabilityId`.
3. **Add the in-memory implementation** to `core/…/store/InMemoryStores.kt` so behaviour is testable
   with no device.
4. **Write the logic** in `:core` against the port.
5. **Write the suite** in `core/src/test/kotlin/…` extending `Suite("group/name")` and register it in
   `AllSuites.all`.
6. **Register capabilities** in `CapabilityCatalog` with honest statuses, including the
   `NOT_POSSIBLE` entries and their Android limitations.
7. **Run `./tools/verify_all.sh`** and only then implement the Android adapter in `:app`.
8. **Update the docs** — `ROADMAP.md` status, and `PRIVACY.md`/`SECURITY.md` if the subsystem touches
   stored data or permissions.

## Releasing

No signing material is committed, and `*.jks`, `*.keystore`, `keystore.properties` and
`signing.properties` are gitignored. `assembleRelease` produces an unsigned APK; supply your own
keystore and a `signingConfig` locally. Release builds enable R8 minification and resource shrinking,
so any reflective access added later needs a ProGuard rule.

## Continuous integration

`ci/github-actions.yml` is a complete workflow: an offline job (no SDK, runs the three checks above)
and an Android job (real SDK, Gradle tests, `assembleDebug`). It lives in `ci/` rather than
`.github/workflows/` because the automation token used here lacks the `workflows` permission and
GitHub rejects such pushes outright. `ci/README.md` has the two-command procedure to move it into
place.

## Known constraints of this environment

Recorded so nobody re-derives them:

- Maven Central, Google Maven and `services.gradle.org` are unreachable from the sandbox, so the
  Gradle path cannot resolve AGP or AndroidX here. The offline toolchain is not a fallback; it is the
  path that works.
- GitHub release assets redirect to a blocked host, so tooling is obtained via npm, PyPI or a git
  clone instead. GitHub's own runners are not subject to this.
- `apt-get` mirrors are blocked and the system Python is externally managed; a venv supplies the JRE
  used for offline runs.
