# Development

## Two ways to build

**Offline** — no Android SDK, no Gradle, no network. This is the primary path and the one CI runs
first:

```bash
./tools/verify_all.sh
```

**Gradle** — the normal Android path, when a toolchain and network are available:

```bash
./gradlew :core:test :app:test     # the same assertions, through a thin JUnit bridge
./gradlew assembleDebug            # debug APK (applicationIdSuffix ".debug")
./gradlew assembleRelease          # unsigned release APK; supply your own keystore
```

Both paths run *identical* assertions. `core/src/test/kotlin/…/AllSuites.kt` is the single registry:
`LocalTestMain` (offline) and `CoreSelfTestJUnit` (Gradle) both iterate it, so the two runners cannot
drift apart. Adding a suite means adding one line there.

## The offline toolchain

`tools/local_core_check.sh` needs only two things and will look for them in this order:

| Tool | Env override | Default lookup |
|---|---|---|
| Kotlin compiler | `KOTLINC=/path/to/kotlinc` or `KOTLIN_HOME=/path/to/dist` | `kotlinc` on `PATH`, then `/tmp/kc/node_modules/kotlin-compiler/bin/kotlinc` |
| Java runtime | `JAVA_HOME` | `java` on `PATH` |

If neither is found it downloads `kotlinc` to `/tmp/kotlinc-dist` and re-executes itself. Compilation
targets JVM 17.

`tools/local_android_check.sh` additionally needs `android.jar` for API 35:

| Source | Notes |
|---|---|
| `ANDROID_JAR=/path/to/android.jar` | explicit |
| `$ANDROID_HOME/platforms/android-35/android.jar` | a normal SDK install |
| `.tools-cache/android-35/android.jar` | gitignored cache |
| `github.com/Sable/android-platforms` (sparse checkout) | community-maintained `android.jar` for every API level; fetched into the cache |

Two details that are easy to get wrong and are handled by the script:

- `kotlinc` must be invoked with **`-no-jdk`** when `android.jar` is on the classpath. Without it the
  JDK's own `java.*` classes collide with the ones inside `android.jar`.
- `:app` references `R.layout.*` / `R.id.*`, and the real `R` class is generated by AAPT2. Offline,
  `tools/generate_local_r.py` produces an equivalent `R.kt` from `res/` so type-checking can proceed.
  It is generated into `build/`, never committed.
- Test sources compile with `-Xfriend-paths`, which is what the Kotlin Gradle plugin does for a test
  source set. Without it the offline runner would be *stricter* than `./gradlew :core:test` and suites
  could not reach internal collaborators such as the NLU rule table.

## What each check enforces

```
tools/verify_all.sh
 ├─ tools/local_core_check.sh      :core compiles, and every suite in AllSuites passes
 ├─ tools/validate_android.py      resources, manifest and view references are self-consistent
 └─ tools/local_android_check.sh   :core + :app type-check against real android.jar (API 35),
                                   then the app's own offline suites run on the JVM
```

`validate_android.py` is what catches the class of bug that otherwise only appears on a device: a
layout id referenced from Kotlin but missing in XML, a manifest component whose class does not exist,
a `@string/` that was never declared, a theme that is not defined. It parses the XML directly, so it
needs no Android tooling.

## Conventions

These are not stylistic preferences; each one exists because the alternative produced a bug.

**`:core` never imports `android.*`.** Not even for a constant. If a piece of logic seems to need the
platform, it needs a port instead. This is what makes the whole brain of the assistant testable in
milliseconds, and `validate_android.py` plus the type-check will both fail loudly if it is violated.

**Framework APIs only, `findViewById` not view binding.** View binding generates classes implementing
`androidx.viewbinding.ViewBinding`, which would drag in AndroidX and break the zero-dependency rule.

**A capability that cannot work says so.** Port methods return `PortResult`, and `Denied` carries a
`capabilityId` that maps to a catalogue entry with a status, an explanation, a remedy, and — for
`NOT_POSSIBLE` — the `androidLimitation`. Never return a success-shaped default for something that did
not happen.

**Time comes from `ClockPort`.** No `System.currentTimeMillis()` in logic; inject the clock and use
`FixedClock` in tests. Every temporal test in the repo pins a known local instant and computes the
expected value independently rather than reading it back from the parser.

**Comments explain *why*, not *what*.** The codebase is heavily commented, but the comments carry the
reasoning that would otherwise be lost: why a rule is narrow, why a fraction is 0.55/0.45, why a
negation guard exists, which real failure a line prevents. If a comment restates the code, delete it.

**Test names are sentences about behaviour.** `"an explicit evening time beats the daypart word next
to it"`, not `"testParseEvening"`. A failing suite should read as a list of broken promises.

**Deterministic before clever.** The NLU is a rule table, the embedder hashes, the lexical index is
BM25, the crypto is pure Kotlin. Neural components are *slots* (`LocalModelPort`, `IntentReranker`)
that can only adjust what the deterministic layer already produced.

## Adding a subsystem

The order matters, because each step keeps the build green:

1. **Model it** in `core/…/model/` — plain data classes, no Android, no I/O.
2. **Declare the port** in `core/…/ports/` returning `PortResult`, with `Denied` carrying a
   `capabilityId`.
3. **Add the in-memory implementation** to `core/…/store/InMemoryStores.kt` so behaviour is testable
   with no device.
4. **Write the logic** in `:core` against the port.
5. **Write the suite** in `core/src/test/kotlin/…` extending `Suite("group/name")` and register it in
   `AllSuites.all`.
6. **Register capabilities** in `CapabilityCatalog` with honest statuses, including the
   `NOT_POSSIBLE` entries and their Android limitations.
7. **Run `./tools/verify_all.sh`** and only then implement the Android adapter in `:app`.
8. **Update the docs** — `ROADMAP.md` status, and `PRIVACY.md`/`SECURITY.md` if the subsystem touches
   stored data or permissions.

## Releasing

No signing material is committed, and `*.jks`, `*.keystore`, `keystore.properties` and
`signing.properties` are gitignored. `assembleRelease` produces an unsigned APK; supply your own
keystore and a `signingConfig` locally. Release builds enable R8 minification and resource shrinking,
so any reflective access added later needs a ProGuard rule.

## Continuous integration

The live workflow is **[.github/workflows/build-apk.yml](../.github/workflows/build-apk.yml)**
(name: `Build Android APK`). It runs on every push to `main` and on demand via `workflow_dispatch`,
and it exists so that an installable APK can be produced without Android Studio, a local SDK or any
signing material.

| Job | What it runs | Needs |
|---|---|---|
| `verify` | `tools/local_core_check.sh` (all 247 `:core` checks incl. every NLU test), `tools/validate_android.py`, `tools/local_android_check.sh` | JDK 17 + kotlinc only |
| `build-apk` | `sdkmanager --install platform-tools platforms;android-35 build-tools;35.0.0`, then `./gradlew :app:assembleDebug --stacktrace --no-daemon`, then an APK sanity check | full Android SDK |

`build-apk` declares `needs: verify`, so no APK is ever published from a run where the offline
foundation is red. The artifact is `android-debug-apk` — one file, `app-debug.apk`, 30-day retention.

Three details that are easy to get wrong and are therefore enforced in the file:

- **`compileSdk` is read from `app/build.gradle.kts`, not restated.** `gradle.properties` sets
  `android.builder.sdkDownload=false`, so Gradle refuses to download a missing SDK component; CI must
  install exactly the platform the project compiles against. A guard step fails the run if the two
  disagree, and another fails if `targetSdk > compileSdk`.
- **Gradle and AGP versions are never pinned in the workflow.** The build goes through the committed
  wrapper (`gradle/wrapper/gradle-wrapper.properties` → Gradle 8.11.1) and the version catalog
  (`gradle/libs.versions.toml` → AGP 8.7.3, Kotlin 2.0.21). Even the kotlinc used by the `verify` job
  is derived from that catalog, so the offline checks cannot drift from the Gradle build.
- **Nothing may hide a failure.** No `|| true`, no `continue-on-error`, no `if: always()` on build or
  upload steps, and `if-no-files-found: error` on the upload. A run that produces no APK is red.

### Validating the workflow locally

GitHub only executes workflows on its own runners, but the file itself can be checked offline:

```bash
python3 tools/validate_workflow.py --require-yaml
```

It parses the YAML and asserts the triggers, permissions, action revisions, artifact name and path,
the Gradle task used, agreement between the workflow and `gradle/` on every version, the absence of
the failure-hiding patterns above, plus `bash -n` and strict-mode on every embedded shell script.
It is step 4 of `./tools/verify_all.sh` (skipped, with a message, if PyYAML is not installed).

### Not automated yet

The `verify` job runs the *same* assertions `./gradlew :core:test` would, through the shared
`AllSuites` registry, so test coverage is not lost. What is deliberately not in CI yet:

- Gradle-executed unit tests (`:core:test`, `:app:testDebugUnitTest`) — the JUnit bridges exist and
  work locally, but they add a second execution path for identical assertions.
- `./gradlew :app:lintDebug` — `tools/validate_android.py` already covers resource, manifest and view
  id consistency; Android lint adds little while the UI layer is this thin, and `lint.abortOnError`
  is `false` in `app/build.gradle.kts` anyway.
- Report artifacts (`core/build/reports/**`, `app/build/reports/**`).
- Any release build or signing step — see [Releasing](#releasing).

## Building an APK without Gradle or the Android SDK

`tools/build_apk_offline.sh` exists for environments where the Gradle path is unavailable — no
`services.gradle.org`, no `dl.google.com`, no Maven mirror. It performs the same five
transformations AGP performs, in the same order:

| Step | Tool | Input → output |
|---|---|---|
| 1 | `aapt2 compile` / `aapt2 link` | `res/` + manifest → `base.apk` (`resources.arsc`, `res/`, binary manifest) and `R.java` |
| 2 | `kotlinc` | `:core` + `:app` + `R.kt` → JVM class files, `-no-jdk -jvm-target 17 -Xjvm-default=all` against `android.jar` |
| 3 | `d8` | class files + `kotlin-stdlib.jar` → `classes.dex` (`--min-api 26 --lib android.jar`) |
| 4 | `zipalign` | `resources.arsc` stored uncompressed and 4-byte aligned — mandatory for `targetSdk >= 30` |
| 5 | `apksigner` | v1 + v2 + v3 signature with a throwaway debug key generated by `keytool` into `build/` |

Everything it needs is read out of the build scripts, never restated: `applicationId` +
`applicationIdSuffix`, `namespace`, `versionName` + `versionNameSuffix`, `versionCode`, and the three
SDK levels. Two things AGP does that a plain `aapt2 link` does not are reproduced explicitly: the
manifest `package` attribute is set to the debug application id, and the two relative class names
(`.JarvisApplication`, `.ui.MainActivity`) are expanded against the **namespace** — not the
application id — exactly as the manifest merger would. `--debug-mode` sets `android:debuggable="true"`
the way the debug build type does.

`R.java` is re-expressed as Kotlin because there is no `javac` in this toolchain. The ids are
aapt2's real ones, and the script fails rather than emit an empty `R` — an `R` class whose ids
disagree with `resources.arsc` compiles fine and then crashes at the first `findViewById`.

### What it is not

No manifest merger (there is one manifest), no `BuildConfig` (nothing reads it), no resource
shrinking or R8 (both are off for debug anyway), no lint, no `META-INF/…/app-metadata.properties`.
The output installs and runs, but `./gradlew :app:assembleDebug` and
`.github/workflows/build-apk.yml` remain the reference builds.

### Tool provenance

The script downloads nothing; it uses what is already on disk and every path is overridable
(`AAPT2`, `ZIPALIGN`, `D8_JAR`, `APKSIGNER_JAR`, `ANDROID_JAR`, `BUILD_TOOLS_DIR`, `KOTLINC`,
`JAVA_HOME`). Defaults come from `.tools-cache/`, which is gitignored: `android.jar` API 35 from the
same public mirror `tools/local_android_check.sh` already uses, and build-tools 35.0.0 — the exact
version the CI workflow installs through `sdkmanager`. Point it at a real SDK
(`BUILD_TOOLS_DIR=$ANDROID_HOME/build-tools/35.0.0`) and nothing else changes.

### It found a real bug

The first offline link failed with `resource style/Jarvis not found`. That is not an artifact of this
script: aapt2 resolves a dotted style name with no explicit `parent` as a child of the style named by
its prefix, so `Jarvis.Card` requires a style `Jarvis` to exist. `res/values/themes.xml` declared
three dotted styles with no such parent, which means **`./gradlew :app:assembleDebug` and the CI
workflow would have failed the same way**. The base style was added, and
`tools/validate_android.py` gained `check_style_hierarchy()` so the rule is enforced offline by
`./tools/verify_all.sh` instead of being discovered by a build.

## Known constraints of this environment

Recorded so nobody re-derives them:

- Maven Central, Google Maven and `services.gradle.org` are unreachable from the sandbox, so the
  Gradle path cannot resolve AGP or AndroidX here. The offline toolchain is not a fallback; it is the
  path that works.
- GitHub release assets redirect to a blocked host, so tooling is obtained via npm, PyPI or a git
  clone instead. GitHub's own runners are not subject to this.
- `apt-get` mirrors are blocked and the system Python is externally managed; a venv supplies the JRE
  used for offline runs.
